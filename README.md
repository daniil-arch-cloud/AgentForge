# AgentForge — автоматическая эволюция инструкции LLM-агента

> **Учебный исследовательский прототип**: автоматическая генерация, тестирование и отбор системных инструкций для агента, использующего внешние функции (tool calling). Python + Google Gemini API.

AgentForge реализует простой цикл оптимизации инструкций (*prompt evolution*): агент выполняет набор задач; оценщик анализирует числовой ответ и трассу вызовов инструментов; модель предлагает новую системную инструкцию на основе ошибок; система проверяет кандидат на обучающих задачах и принимает его только при улучшении метрик. Отдельный набор HOLDOUT используется исключительно для финальной оценки, а не для выбора инструкции.

**Область эксперимента ограничена:** изменение и сравнение бюджетов двух вымышленных проектов Alpha и Beta. Агент не меняет собственный код, веса LLM или реализацию инструментов — только текст системной инструкции.

## Как устроено

```text
                 ┌──────────────┐
                 │ SYSTEM PROMPT│
                 └──────┬───────┘
                        ▼
               ┌────────────────┐
          ┌───▶│ Gemini + tools │
          │    └───────┬────────┘
          │            ▼
          │    ┌────────────────┐
          │    │ Evaluator      │─── ответ + трасса вызовов
          │    └───────┬────────┘
          │            ▼
          │    ┌────────────────┐
          └────│ Prompt proposal│◀── ошибки на TRAIN
               └───────┬────────┘
                       ▼
            сравнение с базовой версией
                (TRAIN only)
                       ▼
            выбранная версия → HOLDOUT
```

### Три инструмента

- `get_project_budget(project_name)` — получение начального бюджета.
- `apply_percentage_change(project_name, value, percentage)` — применение одного изменения бюджета с учётом знака и промежуточного значения.
- `calculate_percentage_increase(new_value, old_value)` — итоговое процентное сравнение относительно явно заданной базы.

### Как оценивается агент

1. **Numeric accuracy** — совпадение числового процента с эталоном (допуск менее 0,06 процентного пункта).
2. **Relation accuracy** — корректно ли назван больший бюджет.
3. **Answer accuracy** — корректность численного ответа, направления и проверяемых формулировок.
4. **Tool-trace compliance** — вызваны ли нужные инструменты с правильными проектами, аргументами, процентами, промежуточными значениями и базой сравнения.

Встроенный Benchmark воспроизводим: 8 TRAIN и 4 HOLDOUT сценария, начальные бюджеты генерируются с фиксированным seed. Локальные unit-тесты также содержат негативные примеры заведомо неверных трасс. Проверка естественно-языковых формулировок эвристическая, а не полноценная семантическая верификация. Полный локальный набор содержит 31 unit-тест и не требует API-ключа.

## Быстрый запуск (Windows / PyCharm)

Требуется установленный Python и действующий ключ Gemini API **в поддерживаемом регионе**.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

В `.env` укажи личный ключ:

```text
GEMINI_API_KEY=your_private_api_key
```

**Никогда не добавляй `.env` в Git.** Файл уже находится в `.gitignore`.

Локальные тесты (**не требуют API-ключ и квоту**):

```powershell
.\.venv\Scripts\python.exe -m unittest discover -p "test_*.py" -v
```

Перед полным запуском рекомендуется проверка подключения — **один API-запрос**:

```powershell
.\.venv\Scripts\python.exe preflight.py
```

Только если проверка успешна и квота позволяет:

```powershell
.\.venv\Scripts\python.exe main.py
```

Эксперимент последовательно проверит Baseline и Candidate на TRAIN, отберёт инструкцию и оценит выбранную версию на HOLDOUT. Результат сохраняется в `results/experiment_YYYYMMDD_HHMMSS.json`.

Для генерации Markdown-отчёта и SVG-графика из уже сохранённого JSON (без API):

```powershell
.\.venv\Scripts\python.exe make_report.py results\experiment_YYYYMMDD_HHMMSS.json
```

При ошибках `429` (лимит), `400 FAILED_PRECONDITION` (регион), `500/503` или таймаутах эксперимент прекращается **без сохранения полного результата**: такие события нельзя смешивать с неправильными рассуждениями модели. Текущая бесплатная квота пользователя может ограничивать число полных запусков.

## Последний сохранённый эксперимент (22.10.2026)

В репозитории приложен реальный результат запуска `2026-10-22T11:11:15Z` на модели `gemini-3.5-flash-lite`: [`results/published/experiment_20261022_141115.json`](results/published/experiment_20261022_141115.json). Краткий отчёт: [`summary.md`](results/published/summary.md), график: [`accuracy.svg`](results/published/accuracy.svg).

| Набор / метрика | Baseline | Selected |
|---|---:|---:|
| TRAIN answer accuracy (8 задач) | 75% (6/8) | 100% (8/8) |
| TRAIN numeric accuracy | 100% | 100% |
| TRAIN relation accuracy | 100% | 100% |
| TRAIN tool-trace compliance | 100% | 100% |
| HOLDOUT answer accuracy (4 задачи) | 50% (2/4) | 100% (4/4) |
| HOLDOUT numeric accuracy | 100% | 100% |
| HOLDOUT relation accuracy | 100% | 100% |
| HOLDOUT tool-trace compliance | 100% | 100% |

В этом запуске кандидат был принят по правилу, применяемому **только к TRAIN**: ни одна из четырёх метрик не должна ухудшиться и как минимум одна должна улучшиться. Ошибки исходной инструкции были связаны с формулировкой направления сравнения, несмотря на правильное численное значение и корректную трассу инструментов.

**Ограничения результата:** HOLDOUT содержит всего 4 задачи и охватывает тот же тип задач, что и TRAIN. Поэтому 100% на HOLDOUT — предварительный результат, а не доказательство обобщения на произвольные задачи или другие модели. Следующий исследовательский шаг — расширить набор независимых сценариев и провести повторные запуски с разными seed.

Ранее сохранённый эксперимент v5 находится в [`results/historical_v5_20261020_154210.json`](results/historical_v5_20261020_154210.json); он получен старой версией оценщика и приводится только как исторический артефакт. Его показатели нельзя напрямую сравнивать с актуальным запуском без оговорок.

|---|---|

## Ограничения и возможное развитие

- Небольшая предметная область и выборка (8+4) не доказывают универсальность.
- Генерация разных чисел при одинаковых типах задач повышает разнообразие, но не заменяет независимых задач.
- Для обоснованных выводов нужны несколько повторов, другие seed, учёт задержек/стоимости и статистическая неопределённость.
- Проверка объяснения эвристическая и может допускать ложноположительные оценки.
- Используются глобальные объекты для фиксации вызовов; прототип рассчитан на последовательный, не многопоточный запуск.
